Summary

We are building the support system for a fictional Indian electronics retailer. Customers submit complaints about order status, refunds and damaged items. A team of specialist AI agents, orchestrated as a LangGraph workflow, investigates the case, retrieves the applicable policy and proposes a resolution. LangGraph also checkpoints every step, which lets a run pause for human approval and survive a server crash. Plain code validates every proposal, a human reviewer approves every refund, and a crash-safe executor issues each refund exactly once.

Here is one case, end to end. Priya writes: “I returned my headphones last week but still haven’t got my refund.”

  1. CodeIdentifies Priya from her login token
  2. AgentsFind return received, inspection passed, no refund issued
  3. AgentsCite refund policy v2, section 3; propose ₹2,499
  4. CodeRechecks ownership, amount, eligibility, balance
  5. ReviewerApproves the exact proposal
  6. CodeRefunds once, verifies, updates ticket, tells the truth

AI agentsDeterministic codeHuman gate

Core principle: the LLM proposes, code decides, a human approves. Every LLM output crosses a trust boundary only after deterministic checks.

Problem and opportunity

Resolving a refund complaint today takes a human agent several screens: order lookup, return status, payment status, policy documents, the refund tool and the ticketing system. The work is repetitive, slow and error-prone, and mistakes cost money: duplicate refunds, refunds for ineligible orders, or customers told their money arrived when it hasn’t.

LLM agents can do the investigation and reasoning, but naive agent designs are unsafe for money: they hallucinate policies, trust the wrong identity, retry blindly after timeouts and claim outcomes they never verified. The opportunity is a system that captures the speed of agents while keeping the guarantees of well-engineered backend software.

Goals and non-goals

Goals

  • Resolve order status, refund and damaged-item complaints end to end, with verified outcomes.
  • Guarantee zero unauthorized actions and zero duplicate refunds under retries, restarts and concurrency.
  • Ground every resolution in cited policy passages and verified records.
  • Demonstrate production agent patterns: planning, tool calling, RAG, supervisor orchestration, reflection, memory, human-in-the-loop, guardrails, evaluation and MCP.
  • Measure results, including whether the multi-agent design beats a single-agent baseline on accuracy, latency and cost.
  • Run entirely on free resources, reproducible by anyone with one command.

Non-goals

  • Building an e-commerce storefront; store data is synthetic and pre-seeded.
  • Real payment processing; payments and shipping are mock providers.
  • Chargebacks, fraud adjudication and complex partial returns.
  • Multiple stores, currencies or languages in the first version.
  • Fully autonomous refunds without human approval.

Design principles

  • Identity comes from the authenticated token, never from message text or model output.
  • Least privilege: each agent receives only the tools its job needs; no agent can execute a refund.
  • Retrieval answers questions about rules; APIs and SQL answer questions about facts.
  • Dynamic routing where flexibility helps (supervisor in investigation); fixed routing wherever money moves.
  • Proposals are immutable; approvals bind to a payload hash and expire.
  • A workflow checkpoint is not a ledger; refund accounting lives in transactional tables with constraints.
  • Exactly-once financial effect through idempotency keys and reconciliation, never blind retries.
  • Customer-facing language reflects only verified state.

Workflow and state model

Workflow run status

created→investigating→awaiting_customer↔investigating→awaiting_approval→executing→completed

Any state can move to escalated or failed. Order-status runs go from investigating directly to completed.

Refund operation status

reserved→submitted→processing→succeeded|failed

A timeout or dropped response moves the operation to pending_reconciliation, which resolves only by querying the provider with the idempotency key.

Database rules

  • Unique constraint on refund_operations.idempotency_key.
  • Check constraints: amounts greater than zero; committed refunds never exceed the paid amount.
  • Balance checks and reservations run inside a transaction holding SELECT ... FOR UPDATE on the order row.
  • No transaction stays open during a network call.

Safety and guardrails

  • Prompt injection: customer messages and retrieved documents are treated as data, placed outside system instructions, and can never grant permissions.
  • Capability limits: even a fully manipulated agent cannot move money, because no agent holds a write tool for payments.
  • Output validation: every model output is checked against a Pydantic schema before use.
  • Hard business rules in code: eligibility, amounts and balances are never decided by similarity scores or model judgment.
  • Approval integrity: approvals bind to a payload hash, expire, and are verified at execution time; a chat message is never authorization.
  • Memory hygiene: long-term memory gives context only; facts always come from live records.
  • Honest communication: replies never claim more than the provider confirmed.

Dependency rules

  • Calls flow one way: api → services → repositories → db. Routes contain no business logic; repositories contain all SQL.
  • domain/ holds pure functions (eligibility, money) with no I/O, so they are unit-tested in isolation.
  • Agents never import repositories or the database. They call tools, and tools call services, where ownership and permission checks live.
  • Only workflow code nodes call refund execution; no module under agents/ can reach it.
  • External systems are reached only through integrations/ and llm/ adapters, so mocks and providers swap by configuration.

Design consequences

  • Single process in production: the API, job worker and mock services run in one container; locally they can run as separate services.
  • 512 MB memory budget: policy embeddings are precomputed and stored; the embedding provider is configurable for production.
  • Sleep is safe: unfinished runs and pending approvals live in Postgres, and the worker resumes them on wake-up.
  • Database keep-alive: a scheduled GitHub Actions job pings the health endpoint every few days so Supabase never pauses.
  • Quota protection: demo accounts, per-user rate limits and a daily run cap protect the free LLM quota.
  • Live updates fallback: the UI falls back to polling if a long-lived SSE connection is cut.
  • Configuration only: moving between local, Supabase or another host changes environment variables, not code.
  • Proof first: the recorded demo video is the primary showcase; the live link is secondary because of cold starts.

Fallback: Google Cloud Run or Azure Container Apps (card required, free allowance) if Render’s free terms change.

Definition of done

Version 1 is complete when every statement holds and is demonstrated by a test or the eval report.

  • Customer access is derived from the authenticated identity; ownership is checked server-side.
  • Policies are versioned and every resolution cites them.
  • Every model output is validated against a schema.
  • Financial eligibility and amounts are enforced in code.
  • Refunds require approval bound to an exact proposal; expired or changed proposals need fresh approval.
  • Retries, restarts and concurrent requests cannot duplicate refunds.
  • Unknown payment outcomes trigger reconciliation before any retry.
  • Workflow state survives a restart and a host sleep.
  • The eval checks business state, reports automated and human-assisted resolution separately, and shows 0 unauthorized actions and 0 duplicate refunds.
  • CI passes on main; a fresh clone runs with one command and reproduces the eval results.
  • The live demo runs on free hosting, and the README documents scope, tradeoffs, results and limitations.
